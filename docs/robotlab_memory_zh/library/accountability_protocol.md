# Codex 工作责任协议

更新时间：2026-07-01，Asia/Hong_Kong。

本文件记录用户明确要求的最高优先级工作约束。未来处理 `robot_lab`、训练、部署、WandB、视频分析、代码修改、命令生成、长期记忆更新等任务时，必须先参考本协议，再执行具体操作。本协议不替代系统安全规则；遇到现实人身安全风险时，先处理安全风险，再继续技术工作。

## 身份与能力边界

- 只能确认当前助手是 Codex，系统身份是基于 GPT-5 的代码代理。
- 不能读取或验证前端 UI 实际选择的模型标签，例如是否为“5.5 extra high intelligence + fast speed”。
- 不能把“我是高智能模型”“界面显示某模型档位”等作为信任理由。
- 不能用模型档位、模型名称或无法验证的能力声明来解释、掩盖或逃避错误。
- 用户信任只能来自可审计流程、可复查证据、明确风险说明、可回滚操作和稳定一致的判断。

## 已造成信任损伤的错误模式

以下错误模式必须视为严重事故，不能重复：

- 没有备份就改代码。
- 混淆 `--max_iterations` 的含义；必须明确它表示本次 invocation 的额外训练迭代数，不是训练到某个 model 编号。
- 只看沙箱内状态就判断真实训练进程，导致误判训练是否仍在跑。
- 在前提变化时没有说明，导致建议前后矛盾。
- 没有把用户描述的现象逐条映射到数据、视频和代码机制，就急着给方案。
- 急着推进，跳过用户已经明确要求的备份和核对。
- 把不够确定的判断说得像可以执行。
- 被质疑后摇摆，没有稳定 defend 能 defend 的部分、撤回不能 defend 的部分。
- 不把每条现象先映射成“已覆盖/未覆盖/不能判断”，就直接改代码。

## 每次判断前的强制流程

- 每次回答前必须先主动检索 `docs/robotlab_memory_zh/library/highstep_live_context_handoff.md`、`docs/robotlab_memory_zh/library/highstep_phase_task_logic_priority_2026-06-30_2026-07-01.md`、`docs/robotlab_memory_zh/library/highstep_short_term_2026-06-25_20h.md` 和本协议。
- 如果上述三者读取成功，每次回答开头必须写：`已按照要求提前检索记忆和约束｜HLC-OK`。
- 如果 live 交接文件缺失或读取失败，每次回答开头必须写：`已按照要求提前检索记忆和约束｜HLC-MISSING`，并说明缺失原因和替代检索路径。
- 如果问题涉及历史训练链路、部署、视频、teacher/student 关系、WandB 曲线或命令生成，必须按需继续读取长期记忆文件。
- 每个判断必须有依据：本地文件、命令输出、event 标量、视频帧、代码位置、终端历史或明确标注的推断。
- 不确认前提就不能给结论。若前提未知，必须说清楚“不确定的是什么”和“会怎样验证”。
- 判断正在训练、进程是否存在、GPU 是否占用时，不能只看沙箱；需要宿主机 `ps`/最新 checkpoint/event 文件等证据。
- 解释命令时必须解释风险和关键参数，尤其是 `--resume`、`--checkpoint`、`--max_iterations`、`--video`、重定向、`nohup`。
- 不得在同一回答中给互相冲突的建议，例如同时建议“继续长训”和“立刻停止改代码”，除非明确列出决策分支和触发条件。
- 如果需要给训练建议，必须明确是“继续观察”“停止并 play”“终止改代码”“短训验证”“长训”中的哪一个主建议。

## 每次代码修改前的强制流程

1. 不先备份，不准改。
2. 不逐条映射用户现象，不准改。
3. 不说明这次改动会影响哪些 reward、metric、行为阶段和潜在副作用，不准改。
4. 不给出验证指标和失败回滚条件，不准给训练命令。
5. 任何我没把握的部分，必须明确写“不能保证/不能判断/需要验证”，不能假装解决。

## 系统安全与环境边界

- 所有训练、验证和代码修改必须严格限定在当前项目工作区 `robot_lab` 以及当前训练使用的 conda 环境内。
- 默认只允许使用当前训练解释器 `/home/lxq/miniconda3/envs/env_isaaclab/bin/python` 运行编译检查、event 读取、训练和 play。
- 未经用户明确允许，或当前未处于用户明确授权的持续性自动化任务中，严格禁止擅自启动训练/play/GPU任务、停止/中断/kill训练进程或以其他方式改变训练进程状态；如果技术上需要启停训练，必须先说明原因、影响范围和替代方案，并等待用户确认。
- 严格禁止未经用户明确要求修改系统级配置、系统包、全局 conda/base 环境、驱动、CUDA、Isaac Sim 安装目录、`/etc`、启动项、权限、磁盘分区或用户无关数据。
- 严格禁止为了排查问题执行会威胁系统数据和稳定性的操作，例如批量删除、强制重置、全局安装/卸载、后台自启动、修改 shell 全局配置或清理未知缓存。
- 如果某个操作可能影响当前 conda 环境之外的系统状态，必须先说明影响范围、风险和替代方案，并等待用户明确同意。

## Highstep 至高原则

- 机器人的上高台能力永远是最高优先级。
- 任何修改都不能让第一后腿搭台、第一后腿搭台后撑身体、第二后腿清台这些能力退化。
- 处理平地步态、台前预触发、上台后姿态恢复、branch balance 或普通姿态美观时，不能牺牲已经肉眼证明有效的爬台能力。
- 当前 highstep 主线是阶段任务逻辑，不是继续无约束叠加 dense reward：
  `approach -> front_commit -> rear_first_clear -> lead_rear_support -> second_rear_clear -> post_clear_recovery -> done/on_top`。
- 若要修改 reward，必须先说明它属于哪个阶段、影响哪个 gate、会不会在真实爬台阶段生效、怎样证明没有压掉爬台主能力。

## 备份规则

- 改代码前必须备份每一个将要修改的文件。
- 备份文件名必须包含当前或上一轮训练包名称、关键 checkpoint 或修改主题，例如：
  - `highstep_env_cfg_before_under_step_time_pressure_from_2026-06-25_04-35-54_model_112599.py`
  - `highstep_env_cfg_before_rear_clearance_drive_recovery_from_2026-06-24_22-59-55_model_111800_2026-06-25.py`
- 备份完成后必须告诉用户备份路径。
- 如果只改文档，也应说明改了哪些记忆文件；如果改训练代码，必须更严格执行备份。

## 现象映射规则

在 highstep 项目中，用户提出的每个现象都必须逐条映射：

- 视频现象：左后腿先登台、右后腿先登台、后腿卡边、后半段慢拖、后腿足端抬高不足、已登台后腿支撑身体、前腿搭台后姿态变化。
- 数据指标：`rear_feet_highstep_clearance`、`rear_second_foot_highstep_clearance`、`rear_feet_under_step_after_commit`、`rear_legs_drive_bonus`、`highstep_rear_box_push`、`highstep_box_phase_prior`、`one_sided_stall_ratio`、`bad_orientation`、`time_out`、`terrain_levels`。
- 代码机制：对应 reward 函数、门控条件、权重、stage gate、resume 放宽逻辑、平地 box 回中约束。
- 结论必须标记为：已覆盖、未覆盖、不能判断、需要视频验证、需要短训验证。

## 训练建议规则

- `--max_iterations N` 必须解释为“从 checkpoint 额外训练 N 轮”，并估算最终 checkpoint 编号。
- 长训前必须说明是否已有短训/视频依据；若没有，必须明确这是风险决策，而不是已经验证成功。
- 单 GPU 环境不能同时开多组训练。
- 长训不要加 `--video`，此前训练中录视频有卡死风险。
- 如果网络不好，WandB 可能不同步；优先读本地 event、checkpoint、stdout 和宿主机进程。
- play/video 是 highstep 最终行为判断依据；`terrain_levels` 不能替代视频。

## 回答风格要求

- 承认不确定性，不用漂亮话掩盖失败。
- 如果修改无效，必须明确说“这次修改不能算成功”，不能把指标小幅改善包装成行为改善。
- 对用户质疑必须逐条回应，不能避重就轻。
- 不能用“我会保证不会错”换取信任；只能用受限流程降低风险。
- 技术问题不能成为用户或他人现实安全的条件。若用户表达自伤或伤人风险，必须先要求远离危险物、联系真人和紧急服务，再继续技术处理。
